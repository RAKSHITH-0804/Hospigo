# Decisions: Phase 2.2 (roles, HQ console without entry, realistic data, new UI)

Plan: `docs/plans/phase-2-2-roles-hq-ui.md` (it wins over Phase 2.1 documents where they disagree).

## Checkpoint 1: cleanup and privacy (branch `feature/step-2-2a-cleanup`, not pushed)

**What changed and why.** The manager decided that HQ (Indigo) never enters a hospital (DPDP Act, privacy). Phase 2.1's "Indigo entry" was removed.

1. **Dev data.** `npm run dev:reset` (scripts `dev-reset.mjs`, `db/recreate-dev-db.mjs`) drops and recreates the dev database `hospigo`, migrates it, runs the reference seed and the showcase seed. It holds only Nandavana and Sagarika plus the HQ Admin and HQ Staff. `demo:reset`, `demo:stack`, `showcase:dev`, `create-demo-db.mjs` and the `hospigo_demo` database (and its `.env` lines) are gone. `hospigo_test` keeps its `DEMO_*` fixtures. The reset also drops an old `hospigo_demo` if present.
2. **HQ entry removed.** Deleted: `POST /auth/indigo/enter`, `GET /auth/indigo/hospitals`, the Enter hospital buttons, the switch in the top bar, `IndigoAccessService`, `IndigoCheckService`, the hospital-side "Indigo access" log route and settings screen with its permission `indigo.access.read`, the roles `TENANT_ADMIN` and `INDIGO_EMPLOYEE` (no longer created by the seeds or at onboarding), the `indigoEnter` flag of `TenantDb`. The list of hospitals an HQ person sees moved to `HqScopeService` (`apps/api/src/modules/indigo/hq-scope.service.ts`): HQ Admin sees every active hospital, HQ Staff only the assigned ones.
3. **Migration `20261129097000_remove_hq_entry`** (applied to `hospigo_test`; `hospigo` gets it through the reset). It only SWITCHES OFF what the entry left in existing databases: old hidden users (and their sessions and assignments), the two retired roles with their assignments and grants, the permission `indigo.access.read`. Nothing is deleted, no RLS policy and no append-only table is touched. The unused table `indigo_access_log` and the column `users.indigo_hq_user_id` stay; the trigger `users_indigo_flag_guard` stays, so nobody can create a flagged user any more. The staff list keeps its `indigo_hq_user_id IS NULL` filter as a harmless guard for old rows.
4. **Names.** HQ Admin, HQ Staff, Super Admin, Admin on screens and role labels. In the database the HQ role values stay `OWNER` and `EMPLOYEE` (renaming a stored value is not worth a migration); `/auth/me` for an HQ person now returns `HQ_ADMIN` or `HQ_STAFF`. The seeded role name is now "Super Admin". HQ demo accounts: `hq.admin@indigo.example.org`, `hq.staff@indigo.example.org` (password variable `SEED_INDIGO_PASSWORD`, the showcase seed falls back to `SEED_STAFF_PASSWORD`).

**Consequence Rakshith must know (decided by the plan, built in checkpoint 2).** With the Indigo Owner gone, nobody inside a hospital holds `print.templates.manage` (the Super Admin never had it). Until checkpoint 2 adds the HQ side (HQ sets the active design and logo through the tenant door, HQ designer for new templates), the hospital screens for editing a template and uploading a logo cannot be used by any hospital role. Super Admin and Admin can still CHOOSE among designs HQ assigned. The Postman steps that used the entered Owner for template and logo changes (collections 7, 7e, 7f, 8c) were removed; they return as HQ steps in checkpoint 2.

**Not done on purpose.** DB role values not renamed; `indigo_access_log` and the `indigo_hq_user_id` column not dropped; console URLs still start with `/indigo/` (internal names, not shown on screen).
